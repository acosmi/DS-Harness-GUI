# DSH-GUI desktop application

English | [中文](README.zh.md)

The thin Electron assembly for macOS and Windows. It packages the immutable renderer graph and starts the real Harness Host in an Electron utility process. Every application build first removes the previous `dist/` tree, then validates the six release ledgers before emitting new main, preload, utility and renderer artifacts.

The main process constructs the utility-process environment from a closed per-platform list of command-search, user-directory, temporary-directory, locale, and operating-system runtime fields, then adds channel-owned DSH values. Ambient credentials, proxy settings, executable injection options, and capability sockets are excluded by default instead of relying on a list of known secret names. The credential provider can resolve only the inherited `DEEPSEEK_API_KEY` through a narrow main-process bridge and treats that source as read-only, so the official provider can use the key without exposing it to Harness shell subprocesses. Saved credentials and Acosmi OAuth tokens continue through the channel-bound vault bridge. Signed builds require the OS-protected vault and fail closed if its encryption is unavailable or a Linux backend is unprotected or unresolved. An unsigned development build selects that vault when Electron confirms operating-system encryption after app readiness; otherwise it uses process memory, and Linux `basic_text` or unresolved backends never qualify for persistence. The product-info response reports the vault actually constructed for that application lifetime. The vault rejects oversized profile or encrypted files before buffering them and applies fixed limits to each value, the entry count, and the total plaintext in both modes. The utility-side TokenStore converts the bridge's intentionally detail-free failures into a dedicated local error rather than guessing from provider-controlled text.

Normal shutdown destroys the renderer window first so any owned native directory dialog closes, asks the utility process to dispose the Harness tree, keeps the privileged bridge available for required vault cleanup, and then waits for every main-process secret, directory, and browser operation to settle within the same shutdown deadline. A timeout still fails the graceful path and terminates the utility process; it is never reported as quiescent success.

Packaging never gives electron-builder the live monorepo workspace as its project. Each target uses pnpm's shared-lockfile deploy implementation in an owned system temporary directory; pnpm and workspace links are then materialized, and deploy-only dependency specifiers are replaced without modifying hard-linked source manifests. Deploy explicitly disables every dependency lifecycle script and rejects any structured-output lifecycle event, so a cross-architecture target cannot run a native installer against the host architecture; the packager removes every non-target node-pty prebuild and prepares and verifies the target helper itself. The repository's pnpm workspace-state file is restored with its contents, permissions and timestamps, while the isolated deploy leaves workspace `node_modules` intact and does not force a follow-up install. A static workspace-peer check, a recursive staged-filesystem dependency check and utility import smoke, and a final ASAR dependency, application-file, and target-native-binary audit must all pass before Electron fuses are set and the application is signed; the ASAR audit independently rejects any surviving non-target node-pty prebuild.

The product-owned transparent PNG at `assets/branding/dsh-gui-whale-browser-logo-v6.png` is the single source for both macOS and Windows application icons and every renderer product mark. electron-builder converts it to each platform icon format, while the renderer emits it at `branding/dsh-gui-whale-browser-logo-v6.png` under the same integrity manifest as its code and HTML. The isolated package target selects one architecture, while the shared platform configuration declares only artifact formats. The macOS post-pack audit requires the four helpers shipped by the pinned Electron version, validates the reserved EH helper identity if that optional helper is present, and rejects any unrecognized helper until the release identity ledger explicitly records it.

Candidate and stable macOS packaging select the recorded Developer ID Application identity by the exact SHA-1 `A6616C59EA24F8DE1D97ECC8081AE64E3D7D6F61`, avoiding ambiguity with other valid identities in the keychain. A custom signer preserves that SHA-1 through the final codesign invocation instead of allowing electron-builder to replace it with a potentially duplicated certificate common name. Before staging either architecture, the packager removes only that target's named DMG, ZIP, and blockmaps so a failed run cannot leave an old same-name distributable in the candidate set. Both modes require exactly one complete electron-builder notarization credential family. After electron-builder submits and staples the application, the post-sign hook verifies the application deeply and strictly, checks the outer application's channel Bundle ID and hardened runtime, then discovers every packaged Mach-O file and requires each one to contain the recorded leaf-certificate SHA-1, Team ID `Z6BDN8ZHTY`, complete authority chain, secure timestamp, and only the isolated target architecture. It also validates the application ticket and Gatekeeper acceptance. Once DMG and ZIP creation finishes, the packager verifies the final DMG's signature and exact signing certificate before submission; after Apple accepts and the ticket is stapled, it checks the ticket, UDIF integrity, unchanged cdhash, and Gatekeeper acceptance, rebuilds the electron-builder-compatible DMG blockmap from the stapled bytes, then extracts the ZIP and repeats the complete application checks. A local keychain identity is sufficient only for builds on that Mac; CI or another Mac requires a separately protected P12. The repository records no certificate path, CSR path, private key, keychain entry, password, or notarization credential.

Local development packages carry no trusted publisher signature and may build while their recorded external inputs remain blocked. macOS receives an ad hoc signature only so its final bundle can pass structural code-signature verification; Windows development output remains unsigned. A build from modified or untracked source displays its product revision as `dirty:<commit>`. `pnpm run desktop:package:mac:candidate` exists only to produce clean-commit Developer-ID-signed, notarized, stapled arm64 and x64 evidence needed to close the Apple and platform inputs; it neither marks an input ready nor authorizes publishing or stable promotion. `pnpm run desktop:package:mac:stable` additionally requires every recorded production OAuth, SDK, signing, notarization, release-index, legal, platform, and support input to be ready and the frozen product commit to match the checkout.
